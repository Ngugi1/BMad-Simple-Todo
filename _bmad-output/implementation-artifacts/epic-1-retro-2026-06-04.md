## 2. What went well

1. **Test-first discipline never slipped.** Each slice had a verified failing test before implementation (module-not-found, `1..0`, 6 failing `complete` tests, etc.). Nothing was marked done on faith.
2. **Scope discipline was the deliverable, and it held.** Zero dependencies, no scope creep, `N/A` sections stayed `N/A`. The architecture's "resist complexity, don't absorb it" counter-metric was genuinely honored.
3. **The store seam paid off.** `createStore()` factory + single `render.js` formatter + entrypoint-only-printing kept every story a small additive change. Story 1.4 wired the entire CLI with **no domain-code changes**.
4. **Clean, legible history.** One commit per story made the build readable end to end.

## 3. What was challenging (systems, not people)

1. **Spec drift mid-build — the key lesson.** `architecture.md` and `epics.md` were revised to the checkbox View format (`[ ]`/`[x]`) *after* Story 1.2 was implemented in the old strike-through format. The mismatch surfaced only at commit/review time and required a reconciliation commit (`d330084`).
2. **Story entanglement when splitting commits.** Stories 1.1 and 1.2 were both built before the "one commit per story" rule, so they shared `store.js`/`store.test.js`; clean per-story commits required reconstructing intermediate state.
3. **In-memory-across-processes trap (Story 1.4).** CLI state does not persist between `node bin/todo.js` invocations. Mitigated by proving the loop in-process via the exported `execute()` dispatcher; the constraint was named in the story spec, which is why it went smoothly.
4. **Review caught what tests missed.** All 29 tests passed, but none exercised the symlinked `todo` bin, so a main-module-guard bug hid until review. Fixed with a `realpathSync` comparison (`020a67f`).
